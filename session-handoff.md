## Deployment / distribution (scoping discussion — no code yet)
The cost model: cheap routes (draft/loadout/pool/results, and **replay viewing**, which is a client-side iframe) scale to hundreds of users for ~free. The bottleneck is **AI-vs-AI battles** — each pins ~1 CPU core for ~10–40s (`search_parallelism=1`, `search_threads=1`). So **concurrent battles ≈ CPU cores**, and `1000 concurrent users ≈ ~100–250 concurrent battles ≈ ~100–250 cores`. Static hosts (GitHub Pages) and serverless (Vercel/Netlify) are unfit — the app needs a persistent stateful box running Python + the poke-engine Rust binary + a Node Showdown referee. Conclusions:
- **Prereq for *any* public deploy:** run each battle in a supervised subprocess with a hard timeout. Today one hung/flaky battle kills the single uvicorn worker = global outage (see "Battle can wedge the live web app").
- **Server path to 1000:** stateless web tier + Redis sessions + a **battle job queue** (battles are non-interactive, so bursts queue invisibly) + an **autoscaling battle-worker fleet** (1 worker ≈ 1 core, spot instances; battles are deterministic/retryable) + sharded Showdown referees. Cut per-battle cost first (reuse warm Showdown connections, tune search time, cache by `(player_team_hash, boss_id, seed)`) — every 2× halves the fleet.
- **Offline-app path (preferred for zero server burden):** the whole stack already runs on localhost (`make live`), so an app is mostly packaging. **(A)** desktop app via Tauri/Electron bundling the local stack (fast, but big bundle + per-OS code-signing + must **vendor sprites**, forcing the deferred asset/IP decision); **(B, endgame)** WASM PWA — poke-engine→WASM + Showdown sim client-side + rollmons logic ported to JS/Pyodide → pure static hosting, scales indefinitely. Open flags before shipping an app: bundle the now-mandatory sprite assets, and audit bundled-component licenses (Showdown / poke-engine / foul-play) + Pokémon-content IP (fan-project gray area).
